# claim_group_comparator 設計メモ

「書類比較・クレームチェッカー」の解析結果から請求項を取り出し、**比較候補のグループ**を自動で作って、
別タブで並べて見比べるためのブックマークレット。

## 0. この道具が引き受けている問題

請求項の意味を JavaScript で理解して「法的に同一の請求項」を判定することはしない。狙いは、

- 字面
- 段落（構成要件）構造
- 請求項カテゴリー（方法 / 装置 / 回路 / プログラム / 媒体 / システム）
- 引用関係とクレームツリー上の位置

が似ている請求項を**広めに束ね**、そのグループの中で人が細かな文言差を見つけられるようにすること。

したがって次のような差は、**自動で候補から外さない**。外してしまうと、まさに見つけたい差が見えなくなる。

- 主体が違う（ＵＥ / 中継通信デバイス / インフラストラクチャ機器）
- 送信と受信が違う
- 「同じセル」と「異なるセル」が違う
- トリガ条件が違う
- カテゴリーだけが違う（方法 / 装置 / 回路 / プログラム）
- 引用先が違う
- 構成要件が 1 つだけ増減している

「多少過剰でも拾う」を既定（グルーピング強度=**広め**）にしているのはこのため。

## 1. データの出どころ（対象ページ）

| 取得元 | 何を取るか | 備考 |
|---|---|---|
| `#claim_mark` | 請求項の本文 | `CLMNM<n>` を境界に切る。`showCiteCited*`（`[1-1]` 等の表示用番号）は入れ子でも捨てる。`zenki_wdXX` は用語クラスとして拾う |
| `#claim_cite` | 直接引用・独立/従属・カテゴリー末尾語 `『・・方法』` | **引用関係の権威**。引用パターン上限（5000）到達時も全請求項を列挙する |
| `#doc1` / `#doc2` | 解析前のクレームテキスト | フォールバック。`【請求項○】` を検出する |

**`#claim_tree`（罫線ツリー）は使わない。** 上限到達時に黙って欠落する（実測: 92 請求項 → 22 請求項）ため。
`#claim_cite` の「**被**引用請求項」も同じ理由で使わない（打ち切られた不完全な値になる）。
この性質は `fixtures/README.md` に記録されている。

## 3. 段落分割（順序が重要）

**抽出 → 段落分割 → 正規化** の順を必ず守る。正規化は空白を落とすので、先に正規化すると段落境界が消える。

1. 元の改行（`<br>` 由来）
2. 全角空白（U+3000）の連なり ＝ 構成要件区切り。**連なりの長さがインデント深さ**（列挙の入れ子を表す）
3. 行頭の半角インデント
4. ここまでで割れなかったときだけ、句点（常に）と読点（60 文字以上たまっていれば）でフォールバック分割

そのあと、8 文字未満の断片は直前（無ければ直後）の段落へ結合する。
末尾の「方法。」「装置。」のようなカテゴリー宣言がこれで前の段落に吸収され、請求項どうしの段落数が比べやすくなる。

段落番号は**比較画面専用の表示番号**で、元の本文は書き換えない。

## 4. 正規化（比較用の文字列だけ）

請求項全文にも段落にも同じ正規化を使う。

落とす・そろえるもの:

- 解析表示用の番号（`[n-m]`）
- Unicode 正規化（NFKC）＝ 全角・半角の統一もこれで済む
- 英字の大文字・小文字（小文字へ）
- 空白・改行・全角空白（比較用は完全除去。**段落分割は先に済ませておく**）
- 句読点・括弧
- 漢数字 → 算用数字
- **「前記」**（「前記◯◯」と「◯◯」を同じ語として扱うため）

**辞書を持たない。** 定型語の一覧・ストップワード辞書・技術用語辞書・案件別辞書は作らない。
個別に落とすのは「前記」だけで、これは日本語クレームの参照表現そのもの。
「ステップ／手段」のようなカテゴリー差は辞書で畳まず、**全体の一致率に埋もれさせる**
（実測でも文字3-gram の一致率は 0.6 を超える）。

長音符（ー）とダッシュ類は落とさない。落とすと「レポート」が「レポト」になり、
カタカナ語そのものが壊れるため。

引用表現（「請求項◯に記載の…」）だけは citation.js が本文中に見つけた**位置**を丸ごと落とす。
これは語の一覧ではなく構造的な処理で、「引用先が違うだけ」の請求項を遠ざけないために必要。

落とさないもの: 送信/受信、同じ/異なる のような意味的な差。**画面に出す原文も一切正規化しない。**

単語の切り出しは、正規化後の文字列から漢字・カタカナ・英数の連なり（2 文字以上）を拾うだけ。
ひらがなが自然な区切りになるので、形態素解析も辞書も要らない。

## 5. 類似度

単純な指標を重み付きで合成するだけ。機械学習も外部 API も意味解析も使わない。
**重みとしきい値はすべて `settings.js`** にあり、調整のために他のファイルを触らない。

| 配分 | 特徴量 | 重み |
|---|---|---|
| 文字3-gram 40% | `char3` 正規化全文の文字3-gram Dice | 0.40 |
| 共通単語・共通連続文字列 30% | `words` 共通単語 / `char2` 文字2-gram Dice | 0.18 / 0.12 |
| 段落構造 15% | `segCount` 段落数 / `segProfile` 各段落の長さ / `segAligned` 同じ位置の段落の近さ | 0.05 / 0.04 / 0.06 |
| 共通用語クラス 10% | `termClass` `zenki_wdXX` の Jaccard | 0.10 |
| 引用・ツリー・カテゴリー・項種別 5% | `tree` / `category` / `role` / `cite` | 0.02 / 0.015 / 0.01 / 0.005 |

用語クラスは、両方の請求項に 1 つも無ければ**按分から外す**（無い文書で点が下駄を履かない）。
ペア単位でキャッシュするので、100 請求項（4,950 ペア）でも一度しか計算しない。

## 6. 自動グルーピング（4 つの strategy を重ねる）

**サンプルの請求項番号はコードに一切書かない。** すべて実データの構造から導く。
1 つの請求項が複数のグループに属してよい。1 グループ 100 請求項まで。

### tree — 並行サブツリー

複数の独立項を起点とするサブツリーの**形が一致**するとき、DFS 前順の同じ位置どうしを対応させる。
請求項番号の差を固定加算するのではないので、番号が飛んでいても成立する。

**多項従属（2 件以上を直接引用する請求項）は主ツリーの枝に載せない。** 載せると、多項従属に引かれる
独立項のサブツリーだけ形が崩れて対応が取れなくなる（実例: 22・23・24 が 1〜14 を引く出願で、
1 のサブツリーだけ枝が増えて 8・15 と形が合わなくなる）。多項従属は cite strategy が別に拾う。

葉だけの独立項（サイズ 1）は形が同じでも束ねない（全部が 1 つの巨大グループになってしまうため）。

### category — 独立項のカテゴリー

独立項をカテゴリー（方法 / 装置 / 回路 / プログラム / 媒体 / システム）でまとめる。
カテゴリーが同じというだけでは束ねず、平均 `char2` が強度ごとの下限を超えることを要求する。

カテゴリーは `#claim_cite` の `『・・XXX』`（＝末尾語）を第一の出所とし、無い/判定できないときは
本文末尾から推定する。それでも判定できない従属項は**引用先のカテゴリーを継承**する
（「…ＵＥ。」で終わる従属項が、装置系の独立項に従属しているようなケース）。

### text — 字面クラスタリング（種を作って育てる）

「A と B が似ている、B と C も似ている」だけで A・B・C をまとめない。

1. 最も似ているペア（`seedPair` 以上）を種にする
2. 未所属の請求項について、**グループ全体との平均**（`memberAverage`）と
   **どのメンバーとも最低限似ていること**（`memberMinimum`）の両方を満たすものだけを、
   1 件ずつ正式メンバーに加える
3. 一部のメンバーとだけ似ている（`candidate` 以上）ものは確定せず、**追加候補**として別に持つ
4. 種が尽きるまで次のグループを作る

正式メンバーはこの strategy 内で重複させない（帰属を一意にする）。追加候補は確定ではないので、
複数のグループに現れてよい。どのグループにも正式メンバーとして入らなかった請求項は、
最後に「未グループの請求項」としてまとめて出す（手動でグループへ入れられる）。

### cite — 同一引用集合

同じ請求項集合を引用する請求項をまとめる。多項従属が同じ組み合わせを引くケース（21〜24 のような
「装置・媒体・回路」の並び）と、同じ親を引く兄弟従属項どうしの近さの 2 通り。

### 強度プリセット

| | seedPair | memberAverage | memberMinimum | candidate | sibling | category | rootAffinity |
|---|---|---|---|---|---|---|---|
| 広め（既定） | 0.55 | 0.50 | 0.38 | 0.45 | 0.45 | 0.25 | 0.00 |
| 標準 | 0.65 | 0.60 | 0.48 | 0.55 | 0.58 | 0.42 | 0.25 |
| 厳密 | 0.78 | 0.74 | 0.62 | 0.70 | 0.70 | 0.56 | 0.45 |

強度は「グループ数」ではなく「比較候補ペア数」で単調に効く（グループ数は併合が進むと逆に減るため、
テストもペア数で検証している）。

## 7. 新しいタブの作り方（ここが一番の制約）

対象ページの CSP は `script-src 'self'; script-src-attr 'unsafe-inline'`。
`window.open('', '_blank')` で開く `about:blank` は**この CSP を継承する**ので、
新しいタブに script 要素を注入することも eval することもできない。

そこで、**比較タブの中身は親タブの JS から DOM API だけで組み立てる**。
`document.write` も `innerHTML` も使わない（本文は必ず `textContent`）。

- `window.open` は**クリックイベント内で同期的に**呼ぶ（ポップアップブロック回避）。抽出とグルーピングはその後。
- 元タブを閉じると、比較タブの JS 実行主体（親タブのクロージャ）が失われるため**操作はできなくなる**。
  表示中の内容は読めるままなので、親タブの `beforeunload` で比較タブにその旨の案内を出す。
- 比較タブを複数開いても、状態（ストア・編集中の下書き）はタブごとに独立している。

## 8. 表示（100 カードまで）

- 列数は `layout.js` の純関数が、**利用可能な画面幅・カードの最小幅・カード数**から決める。
  カード数だけを見た if 文ではない。`softCap` は「枚数に対して自然な列数」の緩い天井で、
  幅が足りなければ常に幅が勝つ（＝横スクロールを出さない）。
- 最小カード幅は表示密度で変わる（コンパクト 250 / 標準 300 / ゆったり 380 px）。
- **分割描画（requestAnimationFrame での遅延挿入）は使わない。** 実測で上限 100 枚（約 3,900 ノード）でも
  組み立て 5ms・挿入 1ms で終わる一方、rAF はバックグラウンドのタブで発火せず、
  `setTimeout` も背面タブでは 1 秒級に絞られるため、「裏で開いた比較タブが途中までしか描かれない」
  という実害が出た。DocumentFragment へ一括で組み立てて 1 回だけ挿入する。
- 段落選択では画面を作り直さない。カードごとの段落要素の配列を描画時に持っておき、class を付け替えるだけ。
- カードのクリックはグリッド 1 か所へのイベント委譲。

## 8.5 段落の対応付け（segmatch.js）

段落を選んだとき、他のカードで強調するのは「同じ段落番号」ではなく **対応する段落**。
意味は分からないまま、**日本語クレームの書き方に共通する構造**だけを手掛かりにする。
意味解析も動的計画法も学習も使わず、案件固有の語・番号・対応表も持たない。

### 使っている一般則

**(1) 段落を「塊」にまとめる。** 1 つの構成要件が段落に割れていることがあるため。

- 段落の末尾が接続語（又は・若しくは・及び・並びに・かつ…）→ 次の段落と同じ塊
- 次の段落の先頭がその接続語 → 前の段落と同じ塊
- 段落の末尾が「…は、」「…として、」で述語が来ていない → 次の段落と同じ塊
- 次の段落のインデント（全角空白の連なり）が塊の先頭より深い → 同じ塊（列挙の入れ子）

実例: 「…判定したことに基づいて、選択するか、**又は、**」／「…判定したことに基づいて、選択する」は
1 つの構成要件の二択なので 1 塊。「前記◯◯機器は、前記△△として、」＋二択の 3 段落も 1 塊になる。

**表示（原文と段落番号）は塊にせず元のまま分けて出し、反応だけを塊単位にする。**
また塊は「1 つの構成要件かもしれない」という**仮説**にすぎないので、
照合は「塊」と「その中の個々の段落」の両方で行い、良い方を採る
（塊にまとめたせいで本来の対応が消えないようにする）。

**(2) 述語は段落の末尾に来る。** 「…測定レポートを蓄積し」「…蓄積測定レポートを生成し」
「…無線通信ネットワークに対して送信し」は前半がほぼ同文で、違うのは末尾の動作だけ、
ということが普通に起きる。前半の共通部分に引きずられて別の構成要件へ対応しないよう、
**末尾（既定 24 文字）の一致を独立した特徴量として 25%** の重みで見る。

**(3) 向きが逆なだけの対応を認める。** 「◯◯において XX を送信すること」と
「△△において XX を受信すること」は、主体が入れ替わっただけで同じやり取りを指す。
素の文字列と、向きの語（送信/受信・発信/着信・出力/入力…）を畳んだ文字列の
**両方で計算して高い方を採る**ので、向きが同じ一致は最高点のまま、
向きが逆の対応は他に候補が無いときだけ浮かび上がる（畳み込みが誤対応を増やさない）。
この畳み込みは**段落の対応付けだけ**で使い、正規化・グルーピング・表示には効かないので、
送信／受信の違いそのものは今までどおり読める。

**(4) 対応は 1 対 1 とはかぎらない。** 一方で 2 段落に割れている内容が、他方では 1 段落に
まとまっていることがある。最高点から `relatedMargin` 以内の候補と、
**逆向きに引くと選択中の段落へ戻ってくる候補（相互対応）**をまとめて拾うので、
どちらの側を選んでも同じ組が反応する。

**(5) 点が拮抗したときだけ、相対位置（i/n と j/m）が近い方を先に出す。**
構成要件は書かれた順に並ぶので順序は保たれやすい。段落数の違う請求項どうしを比べるため、
絶対的な段落番号ではなく相対位置を使う。

### 配分と誤対応の防止

| 配分 | 見ているもの |
|---|---|
| 共通単語 35% | 正規化後の単語集合の Dice |
| 末尾（述語）25% | 末尾 24 文字の文字3-gram の Dice |
| 文字3-gram 20% | 全体の文字3-gram の Dice |
| 共通する連続文字列 10% | 文字2-gram の Dice |
| 段落の長さ 10% | 短い方 ÷ 長い方 |
| ＋ 用語クラス | 共通する `zenki_wdXX` への小さな加点（按分の外） |

誤った段落を強調するより、何も強調しないことを優先する:

- 最低条件（共通語 2 つ以上／6 文字以上の共通連続文字列／共通用語クラス）を満たさない候補は見ない
- 合計点が `minScore`（0.55）未満なら選ばない
- 十分に対応する段落が無いとき、**同じ段落番号へフォールバックしない**。
  カードには `類似段落なし` と控えめに出す

しきい値の根拠（実データでの実測）: 正しい対応の点は 0.63〜1.00 に集まり、
共通の定型文だけで似ている誤対応は 0.40〜0.52 に収まる。その谷が 0.55。

### 性能

段落ごとの比較用データ（正規化文字列・単語集合・文字3-gram・末尾 3-gram・用語クラス・塊）は
比較タブを開いた時点で全部作ってキャッシュする。クリックのたびに抽出も正規化もしない。
100 カードでも 1 回の選択は実測 30ms 未満。

## 9. グループ編集

`groupstate.js` は純粋な状態管理で、履歴（undo）と JSON 入出力を持つ。
画面はストアを読むだけなので、再描画で手動編集が失われない。

自動再グルーピングは、`source==='manual'` か `manuallyEdited===true` のグループを
**明示的な指示なしに上書きしない**。影響の大きい操作（削除・統合・分割・置き換え・自動状態への復帰）は、
ネイティブの `confirm` ではなく画面内の確認バーで尋ねる（モーダルでページを止めない）。

## 9.5 案件に依存しないこと

**中心処理には、特定の案件の請求項番号・番号差・技術用語・カテゴリー・グループ構成・
ツリー形状を持たせない。** 層で分けている。

| 層 | 知っていること | 知らないこと |
|---|---|---|
| `src/extract/extractor.js` | クレームチェッカーの DOM（`#claim_mark` / `CLMNM<n>` / `#claim_cite` / `zenki_wdXX` / `#doc1`） | 案件の中身 |
| `src/core/*` | 汎用データの形だけ | DOM・ページ・案件 |
| `src/view/*` | 汎用データの形と表示の都合だけ | 請求項の中身 |

接続部分が返す汎用データ（`number` / `rawText` / `segments` / `citations` / `isIndependent` /
`categoryLabel` / `categoryKey` / `termClasses` / `segmentTermClasses` / `normalized`）から先は、
元 HTML の具体的な請求項番号も技術内容も知らずに動く。

前提にしていないこと:

- 請求項番号が 1 から連番であること、欠番が無いこと
- 独立項の数、系列の数、系列ごとの請求項数がそろっていること
- 請求項が番号順に DOM へ並んでいること
- カテゴリーが既知の語のどれかであること
- 段落数が系列間でそろっていること

カテゴリー表（方法・装置・回路・プログラム・媒体・システム…）は**判定の補助**にすぎない。
これは特定案件の用語ではなく日本語クレームの末尾に置かれる一般的な対象語で、表に無い末尾語が
来ても処理は続く（末尾数文字からキーを作り、末尾語ごとに別系列として扱う）。
同様に `normalize.js` の「ステップ / 工程 / 手段」なども、分野語ではなく日本語クレームの
書き方の定型。

想定外のデータで例外が出ても全体を止めない。自動グルーピングが投げた場合は、
「全請求項」1 グループだけの縮退状態で比較タブを開き、その旨を画面内で知らせる。

検証は `tests/generic.test.js`（人工データのみ）が担当する。番号を総入れ替えしても、
技術分野の語彙を丸ごと入れ替えても、**構造が同じなら同じ結果**になることを、
グループを「系列番号:系列内の位置」へ写して突き合わせることで確かめている。

## 10. 意図的に持っていないもの

- 永続化（localStorage / ファイル保存）。タブを閉じるまでの保持。ただし `toJSON()` / `loadJSON()` があるので後から足せる
- 意味解析・法的同一性の判定
- 外部ライブラリ・外部サーバ通信（完全ローカル・オフライン動作）
