## II-1. 対象HTMLから取得できた請求項の実測値

対象: `fixtures/claim-checker/new/書類比較・クレームチェッカー_特願2024-203064.html`
（拒絶理由例.txt と同じ出願 特願2024-203064 のスナップショット）

DOM 構造は推測せず実物を確認した。クレーム解析を実行済みのページでは次の3要素が使え、
**役割を分けて**利用している。

| 要素 | 内容 | 本ツールでの役割 |
|---|---|---|
| `#claim_tree .div_tree` | 罫線ツリー（`  1 ┳  2 ┳  3` / `    ┃    ┣  4 ━  5` …） | **引用関係の一次情報**。解析は `src/core/claim-tree.js`（`claim_relation_writer` から**取り込んだ**独立実装） |
| `#claim_cite` | ページ側が計算済みの一覧（`合計請求項数: 26 (独立請求項: 1,25,26)`、請求項ごとの `引用請求項 / 間接引用 / 被引用請求項 / うち間接被引用 / 引用パターンの数`） | **合計請求項数**と独立請求項。引用関係の照合にも使用 |
| `#claim_mark` | 請求項全文（50,503 文字）。`<span id="CLMNM<n>"><b>【請求項 n】</b></span>` が見出しで、本文には解析用の通番マーカー `<span class="showCiteCitedNoUL">[1-7]</span>` が挿入されている | **請求項全文**と引用表現（引用種別の判定）。ツリーが無い場合の引用関係フォールバック |

**取り込み（vendoring）の方法**: 罫線ツリー記法の解析は自前実装で枝を誤ったため、
`claim_relation_writer/src/core/parser.js` の実績あるアルゴリズム（トークン列＋スタック方式）を
`src/core/claim-tree.js`（`RRB.claimTree`）として**本プロジェクトへ取り込んだ**。
当初は相対パス参照で共有していたが、**プロジェクト間で依存し合わない**というリポジトリ規約
（ルート `README.md`「ルール: プロジェクト間の独立性」）に従い、取り込みに切り替えた。

- 他プロジェクトへの参照は一切なし（`SOURCE_ORDER` に `..` を含めない・`require` で遡らないことを
  ビルドテストで機械的に検証している）
- 取り込んだファイルの冒頭に取り込み元と「一方を直したら他方も直すか判断すること」を明記
- 取り込み側でも独立にテストを持つ（`tests/claim-tree.test.js` 21 件。正常系・不変条件違反・
  循環・実データ）
- ページに残る追加グローバルは `RRB` だけ（ビルドテストで検証）

引用関係はツリーを優先し、請求項本文の引用表現と食い違う場合は上書きせず
`TREE_TEXT_DEPENDENCY_MISMATCH` を警告する。ツリーに現れない請求項は本文から推定し
`CLAIM_NOT_IN_TREE` を警告する。ツリーが不正な記法（`┃` の数が合わない等）の場合、
流用した解析器は救済せずエラーを返す設計なので、**誤った引用関係を黙って生成しない**。

### 構造上の注意点（検出された事項）

1. **拒絶理由が言及する請求項は 1〜20 だが、実際の請求項は 26 まである。**
   初版（拒絶理由の文章のみ）では全請求項数を本文中の最大番号 20 と推定していたため、
   未指摘請求項が「1、8-18」と誤って狭く表示されていた。構造取得により
   **未指摘請求項は「1、8-18、21-26」** に是正された（独立請求項 25・26 が未指摘である点は
   実務上重要）。
2. **請求項20 は請求項19 の下位請求項ではない**（20 の引用元は 1）。拒絶理由には
   「請求項１９には…／請求項２０にも同様の点が指摘される」とあるが、これは引用関係による
   承継ではなく並列の指摘である。本ツールは同様指摘と引用関係による指摘を別欄で保持しているため、
   この違いが表示上も区別される。
3. **拒絶理由の「請求項２、４を引用する請求項５-７」は実構造と矛盾しない。**
   実際は 5→4、6→2、7→2 であり、各請求項の全引用元に記載された引用元のいずれかが含まれる。
   照合はこの包含関係で判定しているため誤検出は生じない（`STATED_DEPENDENCY_MISMATCH` は 0 件）。
4. 請求項本文には全角英数（`ＯＳ`、`ＡｃｃｅｓｓｏｒｙＳｅｔｕｐＫｉｔ`）と半角数字
   （`請求項4に記載`、`2．4ＧＨｚ`）が混在する。照合用テキストの正規化（全角数字→半角、
   ダッシュ類→`-`）を 1:1 長さ保存で行い、表示は原文のままとしている。
5. 通番マーカー `[1-7]` は解析ツールが挿入したものであり請求項の原文ではないため、
   テキスト化の段階で除去している（残すと引用表現の解析と全文表示の双方を汚す）。
6. `#claim_cite` では「被引用請求項」が「引用請求項」を部分文字列として含むため、
   否定後読み `(?<!被)` で区別しないと独立請求項1 が「請求項2〜24 を引用している」と
   誤読される（実際に踏んだ不具合。回帰テストを追加済み）。

## II-2. 追加した整合性検証と検出結果（拒絶理由例 × 実構造）

| 検証 | 実装 | 拒絶理由例での結果 |

合計: エラー 2 件、警告 0 件、情報 5 件（`metadata.issueCounts`）。

指摘漏れの severity 規則は次のとおり（§5.1・§5.4 に対応）。承継性が「強」= 引用元請求項の
文言自体の不明確性・発明特定事項の矛盾・明細書の記載欠如で、下位請求項の限定追加では
通常解消しないもの。

| 条件 | severity | 表示 |
|---|---|---|
| 承継性が強く、問題請求項を**直接**引用 | `error` | エラー |
| 承継性が強く、**間接**引用（多段階） | `warning` | 要確認 |
| 承継性を特定できない指摘 | `warning` | 要確認（限定により解消の可能性あり） |
| 同一理由の他の指摘項目で既に指摘対象 | `info` | 参考（他項目で指摘済） |

同一理由の他項目で指摘済みの場合に `info` へ下げるのは、理由単位で見れば漏れではないものを
エラーとして誤警告しないための設計判断である（`coveredElsewhereInReason` フラグと根拠文で
判別できるようにしている）。

## II-3b. 起動時の自動取得（ユーザ要望による追加）

「ボタンによる手動解析が主になっている。自動で解析して表示してほしい（手動ボタンは残す）」
という要望を受け、**起動時にクレーム構造を自動取得・自動表示**するようにした。

- `launch()` の最後で `RRB.pageClaims.collect(document)` を自動実行する（クリック不要）
- 入力画面に、取得結果のメッセージ（「自動取得: …」）に加えて
  **サマリ行**（総数 ／ 独立請求項 ／ 取得元 ／ 構造警告件数）と、
  `<details>`（既定は閉。「請求項構造を表示（26項）」）で結果画面と同じ請求項構造の表を表示する
  （既定を閉にしたのは、26 行の表で入力欄が画面外へ押し出されるのを避けるため）
- 取得できない場合（クレーム解析が未実行など）は**エラーにせず情報表示**に留め、起動を妨げない。
  拒絶理由の文章だけでも解析できるため、ここで止めるべきではないという判断
- 取得済みの状態で再実行しても再取得しない（取得結果を壊さない）
- 手動の「ページから請求項を取得」ボタンと請求項全文の貼り付けは維持（接頭辞なしの通常文言）
- 拒絶理由の文章の解析（「分析する」）は**自動化していない**。拒絶理由通知の本文は対象ページ上に
  存在せず貼り付けが必要なため、自動実行できる対象がない

### この作業で見つけて直した不具合

再実行時の分岐が、保持しているモーダルのホスト要素が**まだ文書に繋がっているかを確認せずに**
再表示していた。ページ側の描き換え等でホストが外れていると、ブックマークレットを再実行しても
「押しても何も出ない」状態になる（ページを再読込するまで復旧しない）。
`isAttached()` で接続状態を確認し、外れていれば作り直すようにした。
回帰テストを `tests/analyzer-app.test.js` に追加している。

### 起動まわりの自動テスト（`tests/analyzer-app.test.js`・5 件）

依存ゼロの方針のため jsdom は使わず、最小の DOM スタブを自作して連結済みバンドルを実行し、
起動の不変条件だけを検証している（描画内容は検証しない）。

| 検証 | 内容 |
|---|---|
| 自動取得 | 起動時に `pageClaims.collect` がボタン操作なしで 1 回呼ばれる |
| 例外耐性 | `collect` が例外を投げても `launch()` は throw せず、モーダルが表示され `alert` を出さない |
| 異常な戻り値 | `collect` が `undefined` を返しても起動する |
| 再実行 | ホストを重複生成せず、取得済みなら再取得しない |
| 回帰 | ホストが文書から外れていたら作り直す |

## II-6. 追加要件で残した制限

1. **指摘漏れ判定の「承継性」は規則ベースの推定である。** 結論文・要約・明細書記載文の
   語（不明確／整合しておらず／記載されていない）から判定しており、意味理解はしていない。
   判定できない場合は `warning`（要確認）に倒し、根拠文に「追加された限定によって問題が
   解消される可能性があるため、原文を確認してください」と明示する（§5.4）。
   **限定の内容そのものを読んで解消の有無を判断することはできない。**
2. **多項従属・選択的引用は解析実装済みだが、実データでの検証はできていない。**
   対象出願の請求項は全 23 件の従属請求項がすべて単独引用だったため、
   「請求項1又は2に記載の」等や、罫線ツリーで同じ請求項が複数の親に現れる形は
   単体テストのみでの確認である。
3. **請求項の取得はページの「クレーム解析」実行が前提。** 未実行だと `#claim_mark` が空で、
   その場合はエラーメッセージで案内し、請求項全文の貼り付けにフォールバックできる
   （貼り付け経路も同じ解析器を通る）。
4. **ブックマークレットのサイズが 281,775 bytes に増加した**（初版 176KB、取り込みモジュール込み）。
   Chrome/Edge のブックマークとしては動作するが、コメントを保持した可読 1 行化という
   リポジトリ規約の結果であり、サイズが問題になる場合はコメント除去ビルドの追加が必要。
5. **罫線ツリー記法の解析が 2 か所（本プロジェクトと `claim_relation_writer`）に存在する。**
   これはプロジェクト間の独立性を守るための意図的な重複であり、記法の解釈を変える場合は
   両方を確認する必要がある（各プロジェクトが独立にテストを持つ）。
   なお本プロジェクトは他プロジェクトを一切参照しないため、単独コピーでも全機能が動作する。

## 6. 既知の制限・今後の課題（正直な記録）

1. **file:// での完全自動検証は未実施**。ブラウザ拡張が file:// を操作できないため、
   localhost 配信での代替検証とした（実行コード・CSP 環境は同一。差分は origin と clipboard のみ）。
   file:// では第4節の手動手順での確認を推奨。
2. **ブックマークレットサイズ 176,590 bytes（100KB 超の警告）**。リポジトリ規約（コメント保持の
   可読 1 行化・ミニファイなし）に従った結果。Chrome/Edge のブックマークでは動作するが、
   同期環境によっては保存できない可能性がある。必要になればコメント除去ビルドの追加で
   ～半減できる見込み。
3. **文体揺れへの耐性は fixture 準拠の範囲**。「同様のことが言える」「不明りょう」等の
   別表現、実通知冒頭のヘッダブロック（出願番号・起案日・審査官欄）は現サンプルに無いため
   未対応（未知パターンは「未解析・警告」タブに原文のまま表示され、消えはしない設計）。
4. **修正注記の文法は「（修正：Ｘを除く）／（修正：Ｘを追加）」のみ解釈**。その他は原文保持+
   `UNKNOWN_HEADING_NOTE` 警告。
5. **29条系は合成サンプルベース**。実物の 29条通知（備考内の請求項別サブ議論等）での検証が
   今後の課題。備考は原文のまま保持するため情報は失われない。
6. **要約内の数字は半角に正規化される**（例: 請求項2の…）。原文フィールド
   （sourceText・引用文言・見出し raw）は全角のまま完全保持している。
7. 解析に失敗した文・セクションは削除せず `unmatchedSentences` / `unparsedSections` として
   UI の「未解析・警告」タブに表示する。今回のサンプルでは未解析 0 件。
