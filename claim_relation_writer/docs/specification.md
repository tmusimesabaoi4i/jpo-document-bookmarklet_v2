# Claim Relation Writer 仕様書

本書は `Claim Relation Writer` の入力記法・解析アルゴリズム・データモデル・出力規則・状態保存の仕様を定義します。実装・保守を行う人向けの詳細仕様書です。使い方だけを知りたい場合は [`README.md`](../README.md) を参照してください。

対象モジュールは次の4つで、いずれも DOM に依存しない純粋なJavaScriptモジュールです。

| モジュール | ファイル | 役割 |
| --- | --- | --- |
| parser | `src/core/parser.js` | クレーム構造テキスト → 有向グラフ、請求項番号リストテキスト → 番号配列 |
| resolver | `src/core/resolver.js` | 有向グラフ＋指摘・関連請求項 → 影響範囲（5つの集合） |
| formatter | `src/core/formatter.js` | 請求項番号の配列 → 起案文向けの表記文字列 |
| generator | `src/core/generator.js` | 影響範囲＋指摘事項の種類 → 定型文 |

## 1. クレームツリーの入力記法

### 1.1 罫線文字の意味

| 文字 | 役割 | 説明 |
| --- | --- | --- |
| `┳` | 分岐開始 | 直前の請求項を親として分岐を1つ開く。行内でこの直後に現れる請求項の親になり、かつ以降の行で `┣`／`┗` として現れる子請求項の親にもなる |
| `┣` | 分岐の子（継続） | その分岐の子請求項。まだ同じ分岐の兄弟が続く |
| `┗` | 分岐の子（最後） | その分岐の子請求項。これでその分岐を閉じる |
| `┃` | 分岐の継続線 | 行頭に置く。まだ閉じていない外側の分岐がその深さまで続いていることを示す（この後に `┣`／`┗` が続く） |
| `━` | 同列の連鎖 | 新しい分岐を作らず、直前の請求項の子として次の請求項をそのまま連結する |

いずれも「後（行内で右側・または子として続く側）の請求項が、前（左側・親側）の請求項を引用する」という向きになります。

### 1.2 行の文法

1行は次のいずれかとして解釈されます（トークン化した後の並びで判定し、インデントの空白量そのものは見ません）。

- **空行 / `┃` のみの行**: 何もしない（縦線の継続表示のみの行としてスキップ）
- **`┃` を k個 + (`┣` または `┗`) + 請求項番号 + ( (`┳`または`━`) + 請求項番号 )\***: 分岐の深さ k における子請求項の行
- **請求項番号 + ( (`┳`または`━`) + 請求項番号 )\***: 行頭が請求項番号そのものの行（新しい最上位行。後述のとおりスタックをリセットする）

行頭の `┃` の個数を `k` とし、`k` はその行がどの深さの分岐に属するかを表します。`k` と、現在開いている分岐の数（後述のスタックの深さ）は常に `stack.length === k + 1` の関係になっていなければなりません（詳細は「3. 解析アルゴリズム」参照）。

### 1.3 例: `1 ┳ 2 ━ 3` の意味

- `┳`: 請求項1を親として分岐を開始する
- 直後の `2`: その分岐の子。すなわち **2が1を引用する**
- `━`: 新しい分岐を作らず、直前の請求項（2）の子として次を連結する
- 続く `3`: すなわち **3が2を引用する**

まとめると「2が1を引用し、3が2を引用する」という2本の引用関係（辺）が生成されます。

サンプルの木構造1の1行目 `  1 ┳  2 ━  3` はこの形そのもので、辺 `[1,2]` と `[2,3]` が生成されます（`tests/parser.test.js` の完全一致テストで検証済みです）。

### 1.4 多項従属（同一請求項番号の再出現）

請求項番号はグラフ上の1つのノードとして、初出時に作成され、以後同じ番号が現れるたびに同じノードとして扱われます（作れば使い回す＝lookup-or-create）。したがって、同じ番号が複数の位置で「子（引用する側）」として現れれば、その請求項は複数の親請求項を引用している、すなわち多項従属請求項として扱われます。サンプルの木構造2・木構造5の請求項12はこの例です。

また、同一番号が行頭に再掲されても、新しい独立請求項としては扱われません。独立請求項の判定は「一度も子として現れないこと」によって行うため（「4. グラフモデル」参照）、行頭への再掲の有無に影響されません。

## 2. 請求項番号リストの記法（Step 3 の入力）

Step 3 の「指摘する請求項」「関連する請求項」欄は `parseClaimNumberList(text)` で解析します。クレームツリーとは別の、単純な番号リストの記法です。

- 区切り文字: カンマ `,`、全角カンマ `，`、読点 `、`、および空白類（半角スペース・全角スペース U+3000・タブなど、正規表現 `\s` に含まれるもの）。実装上は `split(/[,，、\s]+/u)` で分割します
- 範囲指定: `2-4` の形式。ハイフンは半角 `-` のほか `− － ‐ ~ ～ 〜` も許容します（`/^(\d+)[-−－‐~～〜](\d+)$/`）。開始番号が終了番号より大きい場合、および範囲の差が9999を超える場合はエラーです
- 全角数字は半角に変換してから解釈します
- 重複は除去し、結果は昇順の数値配列で返します
- 空文字列・空白のみの入力は「空のリスト」として扱い、エラーにはしません

## 3. 正規化ルール（`normalizeText`）

クレームツリーの解析前に、以下の正規化を行います。

1. **改行コード**: `\r\n` および単独の `\r` を `\n` に統一します（`replace(/\r\n?/g, '\n')`）
2. **全角数字→半角数字**: `０-９`（U+FF10〜U+FF19）を `0-9`（U+0030〜U+0039）に変換します（`charCodeAt(0) - 0xFEE0`）
3. **罫線異体字の統一**: 下表の細線文字を対応する太線文字に読み替えます

   | 入力（細線） | 変換後 |
   | --- | --- |
   | `┬` | `┳` |
   | `├` | `┣` |
   | `│` | `┃` |
   | `└` | `┗` |
   | `─` | `━` |
   | `｜` | `┃` |

   この対応表にない罫線文字（`═` `║` `╠` `┯` など）は変換されず、トークン化の際に「解釈できない文字」として行番号付きのエラーになります。黙って無視したり、太線と同じ意味だろうと推測したりはしません。

4. **空白の扱い**: 半角スペース・全角スペース（U+3000）・タブは、トークンとトークンを区切る働きしかしません。インデントの幅（列位置）は解析に一切使用しないため、罫線文字さえ正しければ、余白の付け方が行ごとに揺れていても解析結果は変わりません。

## 4. 解析アルゴリズム（トークン列＋スタック法）

### 4.1 トークン化

1行を正規表現 `/(\d+)|([┳┣┗┃━])|(\S)/gu` でスキャンし、次の3種類のトークンに分けます。

- `num`: 連続する数字（正規化により全角数字は既に半角化済み）
- 罫線トークン（`┳`・`┣`・`┗`・`┃`・`━` のいずれか）
- `bad`: 上記のどちらでもない非空白文字（数字でも規定の罫線文字でもない記号や文字）

`bad` トークンが1つでもあればその行は即座にエラー（`解釈できない文字「X」があります`）とし、その行の残りは解析しません。

### 4.2 スタックによる分岐管理

- `stack`: 現在開いている分岐（`┳`）の親請求項番号を、深さの順に積んだ配列
- 行頭の `┃` の個数を `k` とする
- `┣` または `┗` を処理する直前に、必ず次の不変条件を検査します。

  ```
  stack.length === k + 1
  ```

- **`stack.length < k + 1`**（対応する分岐がまだ開かれていない）: エラー「`┣`（または`┗`） に対応する分岐（┳）がありません（┃ の数を確認してください）」
- **`stack.length > k + 1`**（内側の分岐が閉じられていない、または `┃` が足りない）: エラー「内側の分岐が ┗ で閉じられていないか、┃ の数が不足しています」

**なぜ推測で救済しないか**: この不一致は「内側の分岐を `┗` で閉じ忘れた」のか「行頭の `┃` を書き忘れた」のかを、テキストだけからは原理的に判別できません。どちらかに決め打ちして解析を続けると、実際とは異なる請求項番号の親子関係を静かに生成してしまい、起案者が気づかないまま誤った定型文を使ってしまう恐れがあります。曖昧な入力は解析を止めて行番号付きのエラーとして返し、書き手に修正を促す方針を取っています。

処理の詳細:

- `┣` の場合: `parent = stack[k]` として辺を張った後、スタックは変化させない（同じ分岐の兄弟がまだ続く）
- `┗` の場合: `parent = stack[k]` として辺を張った後、`stack = stack.slice(0, k)` として分岐を閉じる（そのグラフの深さの分岐が終わる）
- 行頭が請求項番号の行（`k = 0` かつ数字始まり）: `stack = []` としてスタックをリセットし、新しい最上位行として扱う。このとき未クローズの分岐が残っていてもエラーにしない（行頭に数字が来ることの意味に曖昧さがないため）
- 行の残り部分（1つ目の請求項番号より後ろ）は `(┳ または ━) + 請求項番号` の繰り返しとして処理する。`┳` なら直前の番号を `stack` に push（新しい分岐を開く）、`━` なら何も push せず、直前の番号を親として次の番号への辺を張るだけ

### 4.3 グラフの構築

- `nodes`: `Set` として構築するため、同じ番号が何度現れても1つのノードにまとまります
- `edges`: `[from, to]` のペアの配列。`from + '>' + to` をキーとして重複する辺を除去します（同じ引用関係を複数回書いても1本の辺になります）
- 請求項番号として `1` 未満の値（`0` など）が現れた場合はエラーです
- 同じ請求項が自分自身を引用する形（例: `n ━ n`）はエラーです

### 4.4 循環検出

構文エラーが1つもない場合にのみ、三色（白 / 灰 / 黒）DFSでグラフ全体の循環を検査します。循環が見つかった場合は、経路付きのエラー

```
循環する引用関係が検出されました: 請求項 1 → 2 → 1
```

を返し、`ok: false` とします（この場合 Step 2 以降には進めません）。

### 4.5 エラーの返し方

`parseClaimTree` は最初のエラーで打ち切らず、入力全体を最後まで走査して見つかったエラーをすべて配列で返します（1行の中で最初のエラーが見つかった時点でその行の解析は打ち切ります）。入力が空、またはクレーム番号を1つも含まない場合は「クレーム構造が入力されていません」という単独のエラーになります。

## 6. グラフモデル

```js
graph = {
  nodes: number[],            // 昇順の請求項番号（重複なし）
  edges: [number, number][],  // [from, to] = 「to が from を引用する」
  roots: number[],            // 独立請求項
}
```

- **ノードの統合**: 同一の請求項番号はどこに何回現れても常に同一ノードです（`Set` による管理）
- **辺の向き**: `edges` の要素 `[from, to]` は「`to` が `from` を引用する」ことを表します（`from` = 引用される側 ＝ 親、`to` = 引用する側 ＝ 子）
- **独立請求項（`roots`）の算出方法**: 全ての辺の `to` 側に一度も現れないノードを独立請求項とします。

  ```js
  const dependentSet = new Set(edges.map((e) => e[1])); // 何かを引用している項
  const roots = sortedNodes.filter((n) => !dependentSet.has(n)); // 独立請求項
  ```

  行頭に番号が出現したかどうかでは判定しません。そのため、多項従属請求項が行頭に再掲されていても（＝どこかの辺で `to` になっているなら）誤って独立請求項と判定することはありません。

- **循環検出**: 三色DFS（白＝未訪問、灰＝探索中、黒＝探索完了）を行い、探索中のノードに再訪したら循環と判定します。エラーメッセージには実際にたどった経路をそのまま含めます（例: `請求項 1 → 2 → 3 → 1`）。

## 7. 影響範囲計算（`resolver.js`）

`resolveAffectedClaims(graph, issueClaims, relatedClaims)` は、指摘・関連の各請求項から「引用してくる方向」（`from → to`）へ訪問済み集合付きの幅優先探索（BFS）を行い、影響範囲を求めます。訪問済み集合を使うため、多重経路・多項従属・（万一の）循環があっても重複や無限ループは起きません。

### 7.1 事前検証

1. `graph.nodes` / `graph.edges` が配列でなければエラー
2. 指摘する請求項（`issueClaims`）が1件も無ければエラー
3. 関連する請求項（`relatedClaims`）から、指摘する請求項と重複する番号を除去する（指摘側を優先。関連請求項が指摘請求項の従属項であっても、その関連指定自体はそのまま尊重される）
4. 指摘・関連に含まれる番号のうち、解析済みグラフに存在しない番号があればエラー（該当番号をすべて列挙）

### 7.2 5つの集合の定義

戻り値は1つの配列に統合せず、文ごとに使う集合が異なるため意味ごとに分けて返します。

| 集合 | 定義 |
| --- | --- |
| `issueClaims` | 入力された指摘する請求項（重複除去・昇順）。1件以上必須 |
| `relatedClaims` | 入力された関連する請求項から `issueClaims` との重複を除いたもの（重複除去・昇順） |
| `dependentClaims` | `issueClaims ∪ relatedClaims`（＝`seeds`）を起点に、引用してくる方向へBFSで到達した集合から `seeds` 自身を除いたもの |
| `allAffectedClaims` | `seeds ∪ dependentClaims`（＝BFSの到達集合全体） |
| `citedSeeds` | `seeds` のうち、直接引用してくる請求項（従属項）を1つ以上持つもの |

`citedSeeds` は2文目「請求項Xを引用する請求項…」の主語Xに使う集合です。実装上は、`from → to` の隣接マップ（`children`）で `children.get(s)` が存在し `size > 0` である `seed` だけを残します。誰からも引用されていない seed（＝葉の関連請求項など）は主語に含めません。

```js
// resolver.js の該当部分（抜粋）
const dependentClaims = uniqueSorted([...visited].filter((n) => !seedSet.has(n)));
const citedSeeds = seeds.filter((s) => {
  const c = children.get(s);
  return !!c && c.size > 0;
});
const allAffectedClaims = uniqueSorted([...seeds, ...dependentClaims]);
```

## 8. 番号整形規則（`formatter.js`）

`formatClaimNumbers(numbers)` は請求項番号の配列を、起案文向けの表記文字列に整形します。

1. 重複を除去し、昇順に並べる
2. 連続する番号が**2つ以上**続く場合は「先頭-末尾」の範囲表記にする（1つだけの場合は単独の番号のまま）
3. 連続しないまとまり同士は読点で区切る
4. 数字はすべて全角にする

コードポイントは次の通り固定されています。

- ハイフン: 半角 `-`（U+002D）
- 読点区切り: `、`（U+3001）
- 数字: 全角 `０`〜`９`（U+FF10〜U+FF19。半角の `charCodeAt(0) + 0xFEE0` で変換）

```js
function formatClaimNumbers(numbers) {
  const sorted = [...new Set(numbers || [])].sort((a, b) => a - b);
  const parts = [];
  for (let i = 0; i < sorted.length; ) {
    let j = i;
    while (j + 1 < sorted.length && sorted[j + 1] === sorted[j] + 1) j++;
    parts.push(j > i ? sorted[i] + '-' + sorted[j] : String(sorted[i]));
    i = j + 1;
  }
  return toFullWidthDigits(parts.join('、'));
}
```

例: `[2,3,4,5,6,7,9,10,11]` → `２-７、９-１１`

この整形は、生成文中に現れるすべての請求項番号リスト（1文目の関連請求項、2文目の主語 `citedSeeds` と従属項 `dependentClaims`、3文目の `allAffectedClaims`）に同一の関数を適用します。表記の揺れは起きません。

## 9. 文章テンプレート（`generator.js`）

`generateStatement({ issueType, resolved })` は、`resolver` の戻り値（`ok: true` のもの）から3文構成の定型文を組み立てます。各文は `\n` で連結し、各文の行頭には全角スペース（U+3000）を置きます。

1. **1文目**（関連請求項への言及）: `　請求項{関連}にも同様の点が指摘される。`
   - `relatedClaims` が空なら **この文ごと省略**
2. **2文目**（従属項への波及）: `　請求項{citedSeeds}を引用する請求項{dependentClaims}にも同様の点が指摘される。`
   - `dependentClaims` が空なら **この文ごと省略**
3. **3文目**（結論。指摘事項の種類で文末が変わる）: `　よって、請求項{全体}` + 結論部
   - 明確性（`clarity`）: `に係る発明は明確でない。`
   - サポート要件（`support`）: `に係る発明は、発明の詳細な説明に記載したものでない。`

```js
// generator.js の該当部分（抜粋）
const lines = [];
if (resolved.relatedClaims.length > 0) {
  lines.push('　請求項' + f(resolved.relatedClaims) + 'にも同様の点が指摘される。');
}
if (resolved.dependentClaims.length > 0) {
  lines.push(
    '　請求項' + f(resolved.citedSeeds) + 'を引用する請求項' + f(resolved.dependentClaims) +
    'にも同様の点が指摘される。'
  );
}
lines.push('　よって、請求項' + f(resolved.allAffectedClaims) + type.conclusion);
```

### 9.1 確定仕様（ユーザー確認済み）

計画段階で以下の2点を確認・確定し、実装（および `examples/examples.js` のゴールデンケース）はこの確定仕様に基づいています。

1. **1文目も句点「。」ありで統一する**: 提示された当初の例では1文目のみ句点がない表記でしたが、確認の結果「句点ありで統一する」ことに決まりました。上記テンプレートは1文目・2文目・3文目のいずれも `。` で終わります。
2. **2文目の主語（`citedSeeds`）は、従属項（引用してくる項）を1つ以上持つ請求項のみとする**: 例えば木構造5で指摘＝1・関連＝13を指定した場合、13は誰からも引用されない独立請求項のため2文目の主語には含めず、「請求項１を引用する請求項２-１２にも同様の点が指摘される。」となります（`examples.js` の `case4-uncited-related` 参照）。

## 10. localStorage スキーマ

ローカル版UI（`src/local/app.js`）は、キー `crw.state` に次の形の JSON を保存します。

```js
{
  schemaVersion: 1,
  treeText,             // Step1: クレーム構造の入力（原文）
  issueType,             // Step2: 'clarity' | 'support'
  issueClaimsText,       // Step3: 指摘する請求項（未パースの入力文字列）
  relatedClaimsText,     // Step3: 関連する請求項（未パースの入力文字列）
  graph,                 // 解析済みの引用関係グラフ
  generatedText,         // Step4: 最後に生成した文章
  currentStep,           // 最後にいたステップ（1〜4）
}
```

| フィールド | 内容 |
| --- | --- |
| `schemaVersion` | 常に `1`。読み込み時にこの値が保存データと一致しない場合は、保存データ全体を破棄して初期状態から始める |
| `treeText` | Step 1 の入力（原文のまま） |
| `graph` | 解析済みの引用関係グラフ。**キャッシュ扱い**（後述） |
| `issueType` | Step 2 で選択した指摘事項 |
| `issueClaimsText` / `relatedClaimsText` | Step 3 の入力文字列（パース前） |
| `generatedText` | Step 4 で最後に生成した文章。復元時は再生成照合に合格した場合のみ表示に使う（10.1参照） |
| `currentStep` | 最後にいたステップ番号 |

### 10.1 復元時の扱い

- **`graph` はキャッシュ**: `graph` は保存はされますが、復元時にはそのまま信用せず、`treeText` があれば `parseClaimTree` で再解析した結果を優先して使います（保存された `graph` と `treeText` が何らかの理由で食い違う「デシンク」を防ぐため）。再解析に失敗した場合は `graph` は `null` に戻ります。
- **バージョン不一致・壊れたデータは破棄**: `localStorage.getItem` の内容が `JSON.parse` できない場合、または `schemaVersion` が現在の値と一致しない場合は、保存データ全体を読み込まず「保存なし」として扱います（初期状態から始まります）。
- **`generatedText` は再生成照合に合格した場合のみ復元**: 復元処理（`src/core/session.js` の `restoreState`）は、復元した構造・指摘事項・請求項入力から文章を再生成し、保存されていた `generatedText` と完全一致する場合に限って復元します。生成後に入力だけが変更された「不整合ペア」が保存されていた場合、古い生成文は破棄されます（誤った請求項番号の文章がコピー可能なまま復元されるのを防ぐため）。
- **ステップの補正**: 保存された `currentStep` が1〜4の整数でなければ1に戻します。再解析後に `graph` が得られなかった場合は Step 1 へ、`currentStep` が 4 でも復元できた `generatedText` が無い場合は Step 3 へ戻します（「生成する」の押し直しを促すため）。
- **保存できない環境**: `localStorage` へのアクセスが例外を投げる環境（一部のプライベートブラウジングなど）では、以後の保存処理をすべて諦めてメモリ上の状態のみで動作を継続します。画面にはその旨の注記が表示されます。
- **消去**: Step 4 の「最初からやり直す（保存を消去）」ボタンで `localStorage.removeItem('crw.state')` を実行し、画面の状態も初期値に戻します。

## 11. モジュール構成・責務分担

### 11.1 コアモジュール（`src/core/`）

`parser.js`・`resolver.js`・`formatter.js`・`generator.js`・`session.js` の5つは、いずれもDOMに依存しない純粋なJavaScriptで、次のUMD（Universal Module Definition）パターンで書かれています。

```js
(function (root, factory) {
  if (typeof module === 'object' && typeof module.exports === 'object') {
    module.exports = factory();
  } else {
    root.CRW = root.CRW || {};
    root.CRW.parser = factory();
  }
})(globalThis, function () {
  'use strict';
  // ...
});
```

Node.js（`node --test` でのテストなど）では `module.exports` 経由の CommonJS として、ブラウザ（`file://` での直接読み込みを含む）では `globalThis.CRW` 名前空間経由でそれぞれ読み込まれます。ESモジュールを使わないのは、`file://` で開いた際にESモジュールのCORS制約に引っかかるためです。ビルド工程は不要です。

`generator.js` は `formatter.js` に依存するため、依存モジュールをファクトリ関数の引数として受け取ります（Node.jsでは `require('./formatter')`、ブラウザでは `root.CRW.formatter`）。ブラウザ側で読み込み順を誤り `CRW.formatter` が未定義の場合は、ファクトリの冒頭で例外を投げて即座に気づけるようにしています。

```js
if (!root.CRW.formatter) {
  throw new Error('CRW.formatter が読み込まれていません。script の読み込み順を確認してください。');
}
```

`session.js` は「アプリ状態の整合性」を担うモジュールです（`parser`・`resolver`・`generator` に依存）。UIから独立して次を提供します。

- `invalidateDownstream(state, changedField)`: 上流入力（クレーム構造・指摘事項・請求項指定）が変更されたとき、生成済み文章（構造変更時は解析結果も）を無効化した新しい状態を返します。**古い生成文が「現在の結果」としてコピー可能なまま残ることを防ぐ**、本ツールで最も重要な安全規則です。
- `resolveFromState(state)` / `generateFromState(state)`: 状態オブジェクトから影響範囲の計算・文章生成までを一括で行います。
- `restoreState(saved)`: localStorage の保存データから安全な状態を復元します（型検証・`treeText` の再解析・生成文の再生成照合・ステップの補正）。

#### 1行化（最小URLエンコード）方式

`encodeBookmarklet(body)` は、コメント除去や改行削除ではなく、次の順序の最小URLエンコードで1行化します（順序を変えると正しく動作しません）。

```js
function encodeBookmarklet(body) {
  return 'javascript:' + body
    .replace(/%/g, '%25')
    .replace(/#/g, '%23')
    .replace(/\r\n|\r|\n/g, '%0A');
}
```

**採用理由**: `javascript:` URL中に生の `#` が含まれると（`#claim_tree` 等のセレクタ文字列に必ず出現します）、URLのフラグメント区切りと解釈され、それ以降のコードが失われます。これを避けるために `#` を `%23` にエスケープする必要がありますが、先に `%` をエスケープしておかないと、後続の `#`→`%23` 変換で生成された `%` 自体が二重エンコードされてしまいます。改行は最後に `%0A` へ変換します。ブラウザは `javascript:` URLを実行する際にパーセントデコードしてからスクリプトとして評価するため、実行時には改行が復元され、行コメント（`//`）・ASI・正規表現リテラルなどはすべて壊れません。この方式により、コア5モジュール・`collector-app.js` のソースを一切改変せずにそのまま連結できます。

#### なぜ自己完結インライン方式なのか（CSPとの関係）

対象ページには次のCSPが設定されています（保存ページの `<head>` 内、6行目）。

```
Content-Security-Policy: script-src 'self'; script-src-attr 'unsafe-inline'
```

`script-src 'self'` の下では、外部ドメインからの `<script>` ローダも、実行時のコード評価（`eval`・`new Function`・動的 `<script>` 挿入など）も許可されません。一方、ブックマークレット（ユーザー操作起点の `javascript:` URL）は多くのブラウザでCSPの `script-src` 制約の対象外として実行されるため、**コア5モジュール＋モーダルUIを1つの自己完結インライン `javascript:` URLに収める方式が唯一現実的な配布経路**です。この前提から、`collector-app.js` は実行時コード評価・`document.write`・`<script>` 挿入を一切使わない設計方針を採用しています（DOM APIとクロージャ内の関数だけで完結）。`tests/bookmarklet.test.js` の「CSP衛生」テストが、生成後のバンドル文字列に `eval(`・`new Function(`・`document.write`・`<script` のいずれも含まれないことを検証しています。

#### 抽出仕様（`collector-app.js`）

木構造の抽出は次のセレクタ優先順で行い、最初に見つかった非空要素を採用します（`TREE_SELECTORS`）。

1. `#claim_tree .div_tree` — 常駐の非表示データ保持用要素（「木構造」ダイアログを開いていなくても存在）
2. `#claim_dialog .div_tree` — 「木構造」ダイアログを表示しているときのみ存在
3. `.div_tree` — 上記が見つからない場合の最終手段（`.div_textarea` は複数要素で共有される汎用クラスのため単独では使用しない）

抽出したHTML断片は `treeHtmlToText(html)` で次の順にプレーンテキスト化します。

1. `<br>`（大小文字・自己終了形式を問わず）→ 改行 `\n`
2. 残っているタグをすべて除去
3. 基本エンティティの復元: `&nbsp;` → 半角スペース、`&lt;` → `<`、`&gt;` → `>`、**`&amp;` → `&`（最後に処理）**

`&amp;` の復元を最後に行うのは、他のエンティティ復元より先に行うと二重復元（例: `&amp;lt;` が誤って `<` まで変換されてしまう）が起きるためです。実ページの中身は半角数字・太線罫線5種・`<br>` 行終端のみで入れ子タグや実体参照は含まれませんが、将来のページ側の変更に備えてタグ除去とエンティティ復元を残しています。

#### 状態の安全規則（ローカル版と同一ポリシー＋固有のガード）

- **`session.invalidateDownstream` をそのまま踏襲**: 木構造・指摘事項の種別・請求項指定のいずれかが変わると、ローカル版と同じ `CRW.session.invalidateDownstream` を通して生成済み文章とコピーボタンを即座に無効化します。
- **生成ボタン押下時に明示的な再解析**: `session.generateFromState` は自前で構造を解析しないため、`launch` 内の `ensureParsed()` が生成のたびに `state.graph` の有無を確認し、無ければ `parser.parseClaimTree` を実行します（ローカル版の `ensureParsed` 相当）。解析に失敗した場合は行番号付きのエラーを表示し、生成を行いません。
- **`MutationObserver` による陳腐化検知**: 木構造を収集するたび（起動時・「ページから再取得」時のいずれも）に `bindObserver()` が呼び出され、既存の監視があれば `disconnect` したうえで、そのときの `#claim_tree` 要素に対して `{ childList: true, subtree: true, characterData: true }` で監視を張り直します。収集のたびに張り直すことで、起動時点で `#claim_tree` がまだ存在しない場合や、ページ側が要素ごと差し替えた場合の検知漏れも防ぎます。ページ側で「クレーム解析」が再実行されて中身が変化すると、警告を表示して生成ボタンを一時的に無効化します。モーダルを閉じる際は必ず `disconnect` します。これにより、陳腐化した木構造から気づかれないまま生成が行われることを防ぎます。
- **モーダルはエフェメラル**: 状態は `launch` のクロージャ内にのみ保持され、`localStorage` は使用しません（ページのオリジンを汚しません）。

#### CSS隔離

Shadow DOMは `execCommand('copy')` によるテキスト選択コピーと相性が悪いため採用せず、`#crw-modal` 名前空間の `<style>` 要素をページの `<head>` に注入する方式にしています。Bootstrap Reboot等ページ側の要素セレクタに競り勝てるよう、実際に使用する部品（`button`・`input`・`textarea`・`label`・`details`・`summary`・ラジオボタン等）ごとに明示的なリセットを列挙しています。`z-index` はBootstrapモーダル（1055）を大きく超える `2147483000` 台の値を使い、`pointer-events: none` の背景（`.crw-backdrop`）でページ操作をブロックしないようにしています（木構造が未収集の間もページ側で「クレーム解析」を実行できるようにするため）。jQuery/`$` は使わずバニラDOMのみで実装されています。

## 12. 検証方法

- **`node --test`**（`npm test` から実行可能。`package.json` の `scripts.test` は `"node --test"`）: `tests/` 配下の `parser.test.js`・`resolver.test.js`・`formatter.test.js`・`generator.test.js`・`session.test.js`・`bookmarklet.test.js` を実行します（合計70件）。`examples/examples.js` に定義された木構造1〜6・ゴールデンケースを共通の入力データとして使い、辺集合の完全一致・5つの集合の一致・生成文のバイト単位一致（全角スペース・句点・半角ハイフンまで含む）などを検証します。`session.test.js` は、上流入力の変更で生成済み文章が無効化されること・不整合な保存データから古い生成文が復元されないことの回帰テストです。
- **`bookmarklet.test.js`**: ブックマークレット生成物を対象に次を検証します。
  - **生成物の鮮度**: `scripts/build-bookmarklets.js` を一時的に再実行した結果が、コミット済みの4ファイル（`src/bookmarklet/{new,legacy}/collector.js`・`collector.bookmarklet.js`）と一致すること（改行コードは `\r\n`→`\n` に正規化して比較）。不一致の場合は「npm run build:bookmarklets で再生成してください」という案内付きで失敗します。
  - **1行版の健全性**: `javascript:` で始まる・1行である・生の `#` を含まない・`%` エスケープがすべて正しい形であること・パーセントデコードで元のソースと完全一致すること（ラウンドトリップ）・デコード後が `new Function` で構文エラーにならないこと。
  - **CSP衛生**: バンドルに `eval(`・`new Function(`・`document.write`・`<script` のいずれも含まれないこと。
  - **連結スモーク**: `launch` 呼び出しを除いたコア5+`collector-app.js`をNode上で評価し、`CRW.parser`・`CRW.formatter`・`CRW.resolver`・`CRW.generator`・`CRW.session`・`CRW.collectorApp` がすべて登録されることを確認します（連結順を誤ると各UMDの依存ガードが例外を投げるため、順序ミスを検出できます）。
  - **抽出ロジックの検証**: 合成スタブ入力で `extractTreeText` のセレクタ優先順（`#claim_tree`→`#claim_dialog`→`.div_tree`）・空要素のスキップ・全滅時の手貼り誘導メッセージを検証するほか、リポジトリ共有の `fixtures/claim-checker/{new,legacy}/` 配下の新版/旧版の保存済み実ページHTMLから `#claim_tree` 内の `div_tree` のinnerHTMLを直接取り出し、`treeHtmlToText` で変換した結果が `examples.js` の `tree6`（「書類比較・クレームチェッカー」実ページの1〜24項のツリー）とバイト一致すること、さらに `parseClaimTree` で解析した結果が独立請求項 `1・13・22・23・24` を含む期待どおりの辺集合になることを検証します（ゴールデンケース `case8-checker-page`: 指摘=1・関連=13・明確性、で生成文までバイト一致することも検証済みです）。
- **`tests/browser-test.html`**: 同じ `examples/examples.js` のゴールデンケースをブラウザ上で実行して確認するためのページです。`file://` で開いた場合の動作確認や、`localStorage` が利用可能かどうかの確認も行います。
